# ТЗ: Хау мач — сервис аналитики покупок по чекам

Версия от 13.10.2026. Живая версия документа: https://claude.ai/code/artifact/9b2534db-46f6-4ba9-bd1f-0a2631267317

## 1. Обзор

Веб-сервис автоматически собирает электронные чеки с почты пользователя, раскладывает покупки по отдельным товарам и показывает, на что уходят деньги и как дорожает личная потребительская корзина. Базовые функции бесплатны, расширенная аналитика доступна по подписке Pro.

**Проблема.** Банк видит только магазин и сумму («Пятёрочка, 2 340 ₽»), но не знает, что внутри чека. Траты разбросаны по нескольким банкам и наличным, единой картины нет.

**Аудитория.** Люди 20–40 лет, которые регулярно покупают продукты офлайн и на маркетплейсах (ВкусВилл, Пятёрочка, Магнит, Ozon) и хотят контролировать расходы без ручного ввода.

**Цели проекта:**

- Пользоваться сервисом самому каждую неделю.
- Показать в портфолио фулстек-разработку на TypeScript: интеграции, фоновые очереди, LLM, платежи, аналитику.
- Довести MVP до рабочего состояния за 6–8 недель.

**Не входит в MVP:**

- Прямое подключение к банкам (у российских банков нет открытого API для физлиц).
- Сканирование чеков камерой как основной сценарий.
- Мобильное приложение (веб-версия адаптивная).
- Приём реальных платежей: оплата работает в тестовом режиме ЮKassa.

## 2. Пользовательские сценарии

Ключевой сценарий: пользователь один раз подключает почту, а дальше чеки и аналитика появляются без его участия.

**Бесплатный пользователь**

1. Регистрируюсь по email и паролю, чтобы видеть свои данные.
2. Подключаю почтовый ящик по пошаговой инструкции, чтобы чеки подтягивались автоматически.
3. Вижу список чеков и позиции внутри каждого, чтобы понимать, что именно я купил.
4. Вижу дашборд трат за месяц по магазинам и базовым категориям.
5. Добавляю трату наличными вручную, чтобы картина была полной.
6. Исправляю категорию товара, и сервис запоминает это для следующих покупок.

**Pro-пользователь**

1. Вижу траты по товарным категориям (кофе, сладкое, бытовая химия), а не только по магазинам.
2. Вижу индекс личной инфляции за день, неделю и месяц.
3. Задаю вопрос обычным языком («сколько я потратил на кофе в сентябре?») и получаю ответ с цифрой.
4. Задаю бюджет на категорию и получаю уведомление в Telegram при 80% и 100%.
5. Импортирую выписки нескольких банков и вижу все карты в одном месте.
6. Получаю отчёт за месяц с главными изменениями в тратах.
7. Оформляю, продлеваю и отменяю подписку Pro в личном кабинете.

## 3. Функциональные требования

Разделы 3.1–3.5 входят в MVP, 3.6–3.9 делаются после него.

### 3.1. Авторизация

- Регистрация и вход по email и паролю, подтверждение email.
- Сессия — непрозрачный токен в httpOnly-cookie (SameSite=Lax, 30 дней, продлевается при использовании); в базе хранится только SHA-256 токена. Выход удаляет сессию сразу.
- Сброс пароля по ссылке на почту.
- Удаление аккаунта вместе со всеми данными.

### 3.2. Подключение почты

- Подключение по IMAP с паролем приложения: Яндекс Почта, Mail.ru, Gmail.
- Пошаговая инструкция для каждого провайдера: как создать пароль приложения и включить электронные чеки в приложениях магазинов.
- Проверка подключения сразу после ввода данных.
- Первичный импорт чеков за последние 3 месяца (Pro: 12 месяцев).
- Далее проверка новых писем раз в 15 минут и кнопка «Обновить сейчас».
- Читаются только письма от известных отправителей чеков; список отправителей хранится в конфигурации.
- Статус подключения и время последней синхронизации в настройках; при ошибке входа пользователь видит предупреждение.
- Дальнейшее развитие: персональный адрес для пересылки чеков вместо доступа к ящику.

### 3.3. Разбор чеков

- Из письма извлекаются: продавец, ИНН, дата и время, итог, способ оплаты, фискальные реквизиты (ФН, ФД, ФПД), позиции (название, цена, количество, сумма).
- Парсеры — отдельные модули под каждый формат письма (Ozon, используемые операторы фискальных данных); в MVP не менее 3 форматов.
- Если ни один парсер не подошёл, письмо разбирает LLM по той же схеме; результат проверяется по сумме позиций и итогу.
- Дубли отсекаются по фискальным реквизитам, а при их отсутствии — по продавцу, сумме и времени.
- Неразобранные письма попадают в список «Требуют внимания».
- Исходное письмо хранится 30 дней для переразбора, затем удаляется.

### 3.4. LLM-обработка товаров

- Нормализация названия: «МОЛ.ПАСТ.ПРОСТОКВ.3,2%930Г» → «Молоко Простоквашино 3,2%, 930 г» + базовый товар «Молоко», объём и единица измерения.
- Категоризация по двухуровневому справочнику (например, «Продукты → Молочное», «Здоровье → Анализы»), ответ модели — JSON, проверяется схемой Zod.
- Кэш: одинаковые строки чека не отправляются в модель повторно.
- Правка пользователя имеет приоритет над ответом модели и применяется к будущим покупкам этого товара.
- Бесплатный тариф: категория по продавцу (справочник ИНН → категория), без LLM.

### 3.5. Дашборд и история

- Итог за период и сравнение с прошлым периодом; периоды: день, неделя, месяц, произвольный.
- Траты по категориям, магазинам и дням.
- Топ-10 товаров по сумме за период (Pro).
- История чеков с поиском по товару и фильтрами по магазину, категории и сумме.
- Карточка товара: история цен и магазины, где он покупался.

### 3.6. Личная инфляция (Pro)

- Корзина = базовые товары, купленные не менее 3 раз за период; пользователь может добавить или исключить товар.
- Цена приводится к единице (₽/кг, ₽/л, ₽/шт), чтобы сравнивать разные фасовки.
- Индекс считается как взвешенное изменение цен корзины относительно базового периода (вес = доля товара в тратах); для сравнения показывается официальная инфляция Росстата.
- Периоды: неделя, месяц, квартал, год; топ товаров, которые сильнее всего подорожали.
- Сравнение цен одного товара в разных магазинах, где пользователь его покупал.

### 3.7. Вопросы обычным языком (Pro)

- Чат на отдельном экране.
- LLM переводит вопрос в структурированный запрос (метрика, фильтры, период, группировка). Бэкенд выполняет его сам; сырой SQL от модели не выполняется.
- Ответ: цифра, короткий текст и при необходимости график.
- Лимит: 50 вопросов в сутки.

### 3.8. Бюджеты и уведомления (Pro)

- Месячный бюджет на категорию или общий.
- Привязка Telegram-бота по одноразовой ссылке; уведомления при 80% и 100% бюджета.
- Отчёт за месяц 1-го числа: итоги и 3–5 выводов, сформулированных LLM по уже посчитанным цифрам.

### 3.9. Наличные, выписки, экспорт

- Ручной ввод траты: сумма, категория, дата, комментарий (все тарифы); ввод сообщением в бот «кофе 350» (Pro).
- Импорт выписки CSV из банка (Pro): привязка к карте, сопоставление операций с чеками по сумме и времени (±10 минут), список операций без чека.
- Экспорт чеков и позиций в CSV и XLSX (Pro).

**Оплата через ЮKassa (тестовый режим):**

1. Пользователь выбирает тариф. Бэкенд создаёт платёж с `save_payment_method: true` и ключом идемпотентности, фронтенд перенаправляет на форму оплаты.
2. Статус подписки меняется только по вебхуку `payment.succeeded`, а не по возврату пользователя на сайт.
3. Вебхук проверяется повторным запросом статуса платежа в API ЮKassa; повторная доставка того же события ничего не меняет.
4. За сутки до конца периода фоновая задача списывает оплату сохранённым способом.
5. При неудаче — 3 повторные попытки за 3 дня, затем подписка заканчивается.

**Статусы подписки:**

| Статус     | Что означает                     | Доступ к Pro                     | Куда переходит                                           |
| ---------- | -------------------------------- | -------------------------------- | -------------------------------------------------------- |
| `trialing` | пробный период, 14 дней          | да                               | `active` после оплаты или `expired`                      |
| `active`   | оплаченный период                | да                               | `past_due` при неудачном списании, `canceled` при отмене |
| `past_due` | списание не прошло, идут повторы | да, 3 дня                        | `active` или `expired`                                   |
| `canceled` | автопродление отключено          | да, до конца оплаченного периода | `expired` или `active` при возобновлении                 |
| `expired`  | подписка закончилась             | нет, данные сохраняются          | `active` при новой оплате                                |

**Проверка доступа.** На бэкенде есть одна функция `can(user, feature)` и список лимитов по тарифам в конфигурации. Каждый Pro-эндпоинт проверяет доступ и отвечает `402` с кодом функции. Фронтенд по этому ответу показывает предложение перейти на Pro.

## 6. Архитектура и стек

Монорепозиторий из трёх приложений (веб, API, воркеры) и общего пакета с типами и Zod-схемами. Всё медленное (почта, разбор, LLM, списания) идёт через очередь, поэтому API отвечает быстро.

```
Веб (React) ──REST──▶ API (Fastify) ◀──вебхук── Telegram-бот
                        │   ▲
                        │   └──── ЮKassa (платежи, вебхуки)
           читает/пишет │ ставит задачи
                        ▼          ▼
                  PostgreSQL     Redis (BullMQ)
                        ▲          │ забирает задачи
           пишет результаты        ▼
                        └──── Воркеры ──▶ Почта (IMAP)
                                     └──▶ LLM (Claude / GigaChat)
```

API не ходит в почту сам: он ставит задачу в Redis, воркер забирает письма, разбирает их, отправляет строки в LLM и сохраняет результат в PostgreSQL. В LLM напрямую из API идут только вопросы из чата.

| Слой           | Технологии                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------ |
| Фронтенд       | React, Vite, TypeScript, TanStack Query, React Router, MUI (Material UI), React Hook Form + Zod        |
| Бэкенд         | Node.js 22, Fastify, TypeScript, Zod, Prisma                                                           |
| Очереди        | Redis, BullMQ (повторы с экспоненциальной задержкой, задачи по расписанию)                             |
| Почта          | imapflow, mailparser                                                                                   |
| LLM            | интерфейс `LlmProvider`: Claude через Claude Code CLI (разработка), GigaChat или YandexGPT (продакшен) |
| Оплата         | API ЮKassa, тестовый магазин                                                                           |
| Telegram       | grammY, вебхуки                                                                                        |
| Инфраструктура | pnpm workspaces, Docker Compose, GitHub Actions, VPS + Caddy (HTTPS)                                   |

Структура репозитория:

```
apps/web        — React-приложение
apps/api        — Fastify API
apps/worker     — воркеры BullMQ
packages/shared — типы, Zod-схемы, конфиг тарифов
packages/db     — схема Prisma и миграции
```

## 7. Модель данных

Центр модели — позиция чека (`ReceiptItem`), привязанная к общему справочнику товаров (`Product`): именно эта связь даёт историю цен и личную инфляцию. Суммы хранятся в копейках (`integer`), время — в UTC.

| Сущность                 | Ключевые поля                                                                                                    | Связи                                |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| `User`                   | email, passwordHash, emailVerifiedAt, plan, createdAt                                                            | → всё остальное                      |
| `Session`                | tokenHash, userAgent, lastUsedAt, expiresAt                                                                      | User 1—N                             |
| `MailAccount`            | provider, login, encryptedPassword, status, lastSyncAt, lastUid                                                  | User 1—N                             |
| `RawEmail`               | messageId, from, subject, receivedAt, html, parseStatus, deleteAfter                                             | MailAccount 1—N                      |
| `Merchant`               | inn, name, displayName, defaultCategoryId                                                                        | общий справочник                     |
| `Receipt`                | purchasedAt, totalKopecks, paymentType, fn, fd, fpd, source (`email` / `cash` / `manual`)                        | User 1—N, Merchant N—1, RawEmail 1—1 |
| `ReceiptItem`            | rawName, quantity, priceKopecks, sumKopecks, productId, categoryId, categorySource (`llm` / `user` / `merchant`) | Receipt 1—N                          |
| `Product`                | normalizedName, baseName, unit (`kg` / `l` / `pcs`), unitSize                                                    | общий справочник                     |
| `ItemNormalizationCache` | rawNameHash, productId, categoryId, model                                                                        | кэш ответов LLM                      |
| `Category`               | name, parentId, color, icon                                                                                      | дерево из 2 уровней                  |
| `UserCategoryOverride`   | productId или merchantId, categoryId                                                                             | User 1—N                             |
| `BankTransaction`        | cardLabel, bookedAt, amountKopecks, description, receiptId                                                       | User 1—N, Receipt 0..1               |
| `Budget`                 | categoryId (или null = общий), limitKopecks, period                                                              | User 1—N                             |
| `Subscription`           | plan, status, currentPeriodEnd, paymentMethodId, cancelAtPeriodEnd                                               | User 1—1                             |
| `Payment`                | providerPaymentId, amountKopecks, status, idempotencyKey                                                         | Subscription 1—N                     |
| `WebhookEvent`           | provider, eventId, type, payload, processedAt                                                                    | журнал для идемпотентности           |
| `TelegramLink`           | chatId, linkedAt                                                                                                 | User 1—1                             |

Индексы: `Receipt(userId, purchasedAt)`, `ReceiptItem(productId)`, уникальные `Receipt(userId, fn, fd)`, `RawEmail(mailAccountId, messageId)`, `WebhookEvent(provider, eventId)`.

## 8. API

REST + JSON с префиксом `/api/v1`. Схемы запросов и ответов описаны на Zod и общие для фронтенда и бэкенда; документация OpenAPI генерируется из них. Ошибки в едином формате `{ code, message, details? }`.

| Метод и путь                                                                  | Назначение                                     | Тариф              |

## 9. Нефункциональные требования

Сервис хранит финансовые данные и доступ к почте, поэтому главное требование — безопасность.

**Безопасность**

- Пароли пользователей хешируются argon2id.
- Пароли приложений от почты шифруются AES-256-GCM; ключ только в переменной окружения, не в базе и не в репозитории.
- Из почты читаются только письма от отправителей из белого списка; письма не помечаются прочитанными и не удаляются.
- В LLM уходят только строки чека и агрегаты, без email, имени и номеров карт.
- Вебхуки проверяются (статус платежа запрашивается у ЮKassa, для Telegram — секретный заголовок).
- Rate limit на вход, регистрацию и `/ask`; CSRF-защита для cookie-сессий; строгий CORS.
- Каждый запрос к данным фильтруется по `userId`; на это есть тесты.

**Персональные данные (152-ФЗ)**

- Согласие на обработку данных при регистрации, политика конфиденциальности на сайте.
- Полное удаление данных по запросу пользователя, исходные письма удаляются через 30 дней.
- При запуске для реальных пользователей — серверы в России и уведомление Роскомнадзора; для портфолио достаточно упомянуть это в README.

**Производительность**

- Дашборд и списки отвечают за 300 мс (p95) при 10 000 чеков у пользователя.
- Новое письмо появляется в списке чеков в течение 20 минут; категории от LLM достраиваются асинхронно.
- Ответ на вопрос в чате — до 10 секунд.

**Качество кода**

- TypeScript в строгом режиме, ESLint + Prettier, монорепозиторий на pnpm workspaces.
- Тесты: Vitest для парсеров (на реальных обезличенных письмах), интеграционные тесты API с тестовой базой, Playwright для 3–5 ключевых сценариев.
- CI в GitHub Actions: линтер, проверка типов, тесты, сборка.
- Запуск всего проекта одной командой `docker compose up`. Никаких выдуманных данных в интерфейсе: для локальной проверки — тестовый пользователь admin / admin и своя почта.
- README: скриншоты, схема архитектуры, принятые решения и их причины, известные ограничения.

## 11. Риски и открытые вопросы

Главный риск — магазины могут не присылать позиции чека на почту. Этап 0 нужен, чтобы проверить это до написания кода.

| Риск                                                               | Вероятность | Что делаем                                                                                           |
| ------------------------------------------------------------------ | ----------- | ---------------------------------------------------------------------------------------------------- |
| Магазин не шлёт электронный чек или шлёт только ссылку без позиций | средняя     | Проверить на этапе 0; переходить по ссылке на сайт оператора фискальных данных и забирать чек оттуда |
| Формат письма меняется, парсер ломается                            | высокая     | Запасной разбор через LLM, тесты на реальных письмах, список «Требуют внимания»                      |
| Почтовый провайдер закроет IMAP с паролями приложений              | низкая      | Персональный адрес для пересылки (этап 4)                                                            |
| Локальная модель часто ошибается в категориях                      | средняя     | Переключить `LlmProvider` на GigaChat или YandexGPT, правки пользователя имеют приоритет             |
| Вызовы облачной LLM стоят больше, чем даёт подписка                | низкая      | Кэш нормализации (строки чеков повторяются), лимиты в Pro                                            |
